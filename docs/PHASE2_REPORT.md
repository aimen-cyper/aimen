## 1. ملخص تنفيذي

المرحلة 2 بنت **طبقة منطق العمل كاملة** بين قاعدة البيانات (المرحلة 1) وواجهة تيليجرام (المرحلة 3).
كل ما يفعله البوت لاحقاً — من الضغط على زر إلى خصم الرصيد — سيمر من هنا.

ما يميّز هذه المرحلة أن الدورة الكاملة التي اشترطتَها **تعمل فعلاً الآن**، ويمكنك مشاهدتها
بأمر واحد (`python -m scripts.demo_cycle`) قبل وجود أي واجهة:

> تسجيل → تصفح → طلب → شحن → اعتماد → خصم → إرسال للمزود → متابعة آلية → إكمال → إشعار → سجل → إحصائيات

والمسار البديل يعمل أيضاً:

> فشل المزود → استرجاع آمن → حركة مالية → إشعار المستخدم والأدمن

**الأرقام:** 26 ملف كود إنتاجي (7,001 سطر) + 15 ملف اختبار (3,281 سطراً) = **10,282 سطراً** موثّقة بتعليقات عربية.

## 3. ما نُفِّذ — القرارات المهمة

### 3.1 المال (أهم جزء)

خمسة ضمانات مفروضة بالكود لا بالنية:

1. **لا تعديل رصيد خارج `WalletService`** — لا ملف آخر يكتب في `users.balance_units`.
2. **كل تغيير رصيد يرافقه صف `transactions` في نفس المعاملة** — لا حركة بلا أثر محاسبي.
3. **`reference` فريد لكل حركة** (`payment:12` · `order:34` · `refund:order:34`) — فهرس فريد في قاعدة البيانات يمنع الازدواج حتى لو كرر الكود النداء.
4. **الخصم مشروط ذرّياً** عبر `try_debit`: `UPDATE ... WHERE balance >= amount` — فلا يسمح بسالب تحت أي تزامن.
5. **الدوال المالية تأخذ `tx` من المتصل** — فتندمج في معاملة العملية بدل فتح معاملة منفصلة قد تنجح وحدها.

> اختُبر هذا بسباق حقيقي: 50 طلب خصم متزامن على رصيد يكفي 10 ⇒ نجح 10 بالضبط والرصيد 0.
> و10 استرجاعات متزامنة لنفس الطلب ⇒ استرجاع واحد فقط.

### 3.2 الطلبات

- **الإنشاء ذرّي**: التحقق + الخصم + صف الطلب + سجل الحالة + الإشعار في معاملة واحدة. `public_code = ORD-000123`.
- **منع التكرار بطبقتين**: `client_request_id` فريد (نفس الضغطة المكررة تُعيد نفس الطلب لا طلباً جديداً) + نافذة زمنية لنفس الرابط والخدمة.
- **كل انتقال حالة عبر `_transition` مع `expected_statuses`** — لا تتغير حالة إلا من حالة متوقعة محددة.
- **تصنيف أخطاء المزود** (قرار جوهري):

| نوع الخطأ | التصرف |
|---|---|
| مؤقت (شبكة/مهلة) | إعادة محاولة بتهدئة تصاعدية حتى `MAX_SUBMIT_ATTEMPTS` |
| رصيد المزود غير كافٍ | تأجيل 15 دقيقة + تنبيه يومي للأدمن، ثم فشل بعد `provider_insufficient_wait_hours` |
| دائم (رفض/خدمة غير موجودة) | فشل + استرجاع كامل فوري |
| **غير مؤكد** (انقطاع بعد الإرسال) | `submit_uncertain` + تنبيه أدمن، و**ممنوع إعادة الإرسال آلياً أبداً** (قد يكون الطلب وصل) |
| أي `ProviderError` غير مصنّف | فشل نهائي — لا تخمين |

- **فصل المعاملات حول نداء الشبكة**: حجز وقراءة ⇐ نداء المزود **خارج أي معاملة** ⇐ معاملة قصيرة للتعليم. لا يبقى قفل قاعدة بيانات مفتوحاً أثناء انتظار مزود بطيء.
- **الاسترجاع الجزئي**: طلب 1000 نُفِّذ منه 600 ⇒ يُسترجع فرق الـ400 تلقائياً وتُغلق الحالة `partial`.
- **`auto_refund_on_provider_fail = 0`** ⇒ لا استرجاع تلقائي، لكن تنبيه أدمن صريح للاسترجاع اليدوي. **في الحالتين لا يضيع المال.**
- **`recover_after_restart()`**: الطلبات العالقة في `submitting` بلا رقم مزود تُنقل إلى `submit_uncertain` للمراجعة البشرية، والأقفال منتهية الصلاحية تُحرَّر.

### 3.3 الشحن

- الحدود الفعلية = حد طريقة الدفع، وإلا الحد العام من الإعدادات.
- `requires_proof` يفرض صورة أو رقم عملية؛ ومرجع الحوالة المكرر يُرفض (`DuplicateOperationError`) — كشف إعادة استخدام الإيصال.
- **الاعتماد يبدأ بـ`set_status(expected_status='pending')`؛ إن فشل الشرط يُرفع الخطأ قبل أي إضافة رصيد** — هذا ما يجعل اعتمادَين متزامنَين من أدمنين مختلفين يضيفان الرصيد مرة واحدة فقط (مُختبَر).
- سبب الرفض إلزامي (3 أحرف فأكثر) ويصل للمستخدم. إيقاف طريقة دفع لا يحذفها.

### 3.4 الإشعارات

- **Outbox**: الإشعار صف في قاعدة البيانات داخل معاملة العملية، ومهمة `dispatch_pending` ترسله لاحقاً مع حجز (`lease`) يمنع عاملين من إرسال نفس الإشعار.
- فشل الإرسال **لا يُسقط** العملية المالية.
- التصنيف: مؤقت ⇒ `mark_failed` وإعادة المحاولة · محظور ⇒ `mark_skipped` + `blocked_bot=1` (لا نستنزف الطابور على من حظر البوت) · دائم ⇒ `mark_failed(permanent=True)`.
- **تنبيهات الأدمن تستهدف الصلاحية لا الدور** — من مُنع فردياً من صلاحية لا يصله تنبيهها (مُختبَر).
- مفاتيح منع التكرار دقيقة لكل حدث (`order:12:completed`، `ticket:3:reply:88`) حتى لا يبتلع إشعارٌ آخر.

### 3.5 الأمان والصلاحيات

- 43 صلاحية و4 أدوار، كلها في قاعدة البيانات. **لا أدمن ثابت في الكود**؛ قائمة `SUPER_ADMIN_IDS` في `.env` للطوارئ فقط ولا تمنح صلاحية بذاتها داخل المسارات العادية (مُختبَر).
- استثناءات فردية: يمكن منح صلاحية واحدة لمستخدم دون ترقيته، أو منعه منها رغم دوره — والمنع يتقدم على الدور.
- محاولة الوصول المرفوضة تُسجَّل في `audit_logs` باسم `security.permission_denied`.
- **مفاتيح API**: تُخزَّن مشفَّرة (Fernet)، ويُحفظ منها `api_key_hint` = آخر 4 خانات فقط للعرض. لا تظهر في سجل التدقيق ولا في `provider_requests` ولا في رسائل الواجهة — ولكلٍّ من هذه اختبار.

### البَقّان الحقيقيان اللذان كشفتهما الاختبارات (قبل الواجهة)

1. **`NotificationService._users_with_permission` كان يستعلم عن عمود غير موجود** (`up.is_allowed` بدل `up.allow`) ⇒ `OperationalError` كان **يُسقط كل مسار `notify_admins`**: تنبيه فشل الطلب، تنبيه الحالة غير المؤكدة، وتنبيه الاسترداد بعد إعادة التشغيل. أُصلح واختُبر.
   *الدرس المسجَّل:* أي SQL يدوي خارج المستودعات يحتاج اختبار تكامل يمر به فعلاً.
2. **`claim_pending_for_submit` كان يتجاهل `next_check_at`** ⇒ الطلب الذي فشل فشلاً مؤقتاً يُلتقط فوراً في الدورة التالية، فتُستهلك محاولاته الثلاث في ثوانٍ وتُبطَل تهدئة 15 دقيقة الخاصة بنقص رصيد المزود. أُصلح واختُبر.

## 5. طريقة التشغيل

> المرحلة 2 طبقة منطق، وواجهة تيليجرام تأتي في المرحلة 3. لذلك «التشغيل» هنا = تهيئة قاعدة البيانات + مشاهدة الدورة الكاملة.

```bash
cd smm_bot

# 1) بيئة افتراضية وتثبيت المتطلبات
python -m venv .venv && source .venv/bin/activate      # ويندوز: .venv\Scripts\activate
pip install -r requirements.txt

# 2) إعداد ملف البيئة
cp .env.example .env
python -m scripts.init_db --gen-key                     # ولّد ENCRYPTION_KEY وضعه في .env
#    ثم املأ BOT_TOKEN و SUPER_ADMIN_IDS في .env

# 3) تهيئة قاعدة البيانات (يطبّق الترحيلات 0001 → 0004)
python -m scripts.init_db
python -m scripts.init_db --status                      # عرض الحالة دون تعديل

# 4) مشاهدة الدورة الكاملة تعمل أمامك
python -m scripts.demo_cycle
python -m scripts.demo_cycle --keep                     # إبقاء قاعدة بيانات العرض للفحص
```

`demo_cycle` يطبع 11 خطوة للمسار الناجح و4 خطوات للمسار البديل، وفيها أرقام حقيقية
مقروءة من قاعدة البيانات (الرصيد، رقم الطلب لدى المزود، الحركات المالية، مسار الحالات، الإحصائيات).

⚠️ **بوضوح:** العرض يستخدم قاعدة بيانات مؤقتة (`data/demo_cycle.db`) تُحذف بعد الانتهاء، ومزوداً
وهمياً محلياً بلا أي اتصال شبكي. لا يُستخدم `mock` في الإنتاج — المزود الحقيقي يُنفَّذ في المرحلة 5.

## 7. المشاكل والقيود المعروفة

1. **لا واجهة تيليجرام بعد** — لا `main.py` ولا `handlers/`. الخدمات تُستدعى حالياً من الاختبارات وسكربت العرض فقط. (المرحلة 3)
2. **المزود الحقيقي غير منفَّذ** — `perfect_panel` مسجَّل كـ«مخطط له» ويرفع خطأ صريحاً إن استُدعي، بدل تنفيذ صوري. (المرحلة 5)
3. **المهام الدورية ليست مجدولة** — الدوال جاهزة (`process_pending_orders`, `process_due_orders`, `dispatch_pending`, `expire_due`, `auto_close_idle`, `alert_stuck_orders`) لكن ربطها بـ`JobQueue` يتم في المرحلة 3/4.
4. **`submit_uncertain` يحتاج قراراً بشرياً بالتصميم** — لن يُعاد إرسال الطلب تلقائياً مهما طال الوقت؛ هذا مقصود لمنع الطلب المزدوج، والأدمن يحسمه بـ`admin_mark_failed` أو `admin_link_provider_order`.
5. **الاسترجاع الجزئي يعتمد صدق المزود** في `remains` — إن أبلغ المزود رقماً خاطئاً يُحسب الاسترجاع عليه. سجل `provider_requests` يحفظ الرد الخام للمراجعة.
6. **SQLite كاتب واحد** — التزامن مُختبر ويعمل، لكن الحمل العالي جداً يحتاج PostgreSQL. طبقة المستودعات مكتوبة لتسهيل النقل (لا SQL خاص بـSQLite خارجها إلا ما هو موثّق).
7. **`scripts/demo_cycle.py` أداة عرض وتطوير** وليست جزءاً من مسار الإنتاج — تُحذف أو تُترك حسب رغبتك، ولا يعتمد عليها أي كود آخر.
