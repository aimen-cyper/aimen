## 1. ملخص تنفيذي

المرحلة 3 سلّمت واجهة العميل كاملة، لكن كل عمل الأدمن كان يتم من السكربتات وطبقة الخدمات.
المرحلة 4 نقلت **كل** ذلك إلى داخل تيليجرام: لوحة تحكم عربية بثمانية أقسام، تُبنى أزرارها
من صلاحيات المستخدم الفعلية في قاعدة البيانات، وكل إجراء خطير فيها يمر بتأكيد ثانٍ ويُكتب
في `audit_logs` مع قيمة قبل/بعد، ويصل إشعاره للمستخدم المتأثر عبر صندوق الإشعارات.

بعد هذه المرحلة صار البوت يُدار بالكامل من الهاتف:

```
/admin  →  لوحة التحكم
          👥 المستخدمون   💳 طلبات الشحن   📦 الطلبات   🎫 التذاكر
          🗂 الخدمات       ⚙️ الإعدادات      📋 السجلات   💚 صحة النظام
```

وأصبحت الدورة المالية مغلقة داخل الواجهة: المستخدم يرسل إثبات شحن → الأدمن يراه في
`💳 طلبات الشحن` → يعتمده (أو يعدّل المبلغ، أو يرفضه بسبب) → الرصيد يتغيّر بحركة مالية
واحدة → إشعار للمستخدم → سطر في سجل التدقيق.

**ما لم يُبنَ في هذه المرحلة (مؤجَّل بقرار صريح):**

| المؤجَّل | المرحلة |

| النسخ الاحتياطي من اللوحة + التقارير الموسّعة والرسوم | 10 |

## 3. ما نُفّذ فعلياً

### 3.1 الصلاحيات (RBAC) — لم تعد نظرية

* المزخرف `@admin_required(Permission.X)` يُطبَّق **على كل معالج**، فالضغط المباشر على
  `callback_data` لقسم محجوب يُرفض حتى لو لم يكن الزر معروضاً أصلاً.
* بناء الأزرار يعتمد على `permissions_of(context)`، فلا يرى الأدمن زراً لا يملكه.
* كل رفض يُسجَّل في `audit_logs` بالإجراء `security.permission_denied`.
* لا أدمن ثابت في الكود: الأدوار والصلاحيات تُقرأ من `role_permissions` و`user_permissions`،
  وتغييرها أثناء الجلسة يسري على الضغطة التالية مباشرة (مُثبَت باختبار).

### 3.2 القواعد الإلزامية الأربع (القسم 5 من تصميم المرحلة 0)

| القاعدة | التطبيق |
|---|---|
| فحص الصلاحية على الـcallback نفسه | `admin_required` على 46 معالجاً + فحص ثانٍ داخل الخدمات. |
| تأكيد ثانٍ + منع تكرار للعمليات الخطيرة | شاشة تأكيد + `token` فريد لكل عملية؛ تكرار الرمز يرفع `DuplicateOperationError`. |
| `audit_logs` بقيمة قبل/بعد | تُكتب **داخل الخدمات** لا في المعالجات ⇒ نفس السجل سواء جاء الإجراء من اللوحة أو من سكربت. |
| إشعار المتأثر عبر Outbox | `notify_user_manual` داخل نفس المعاملة، بنفس الـtoken ⇐ لا إشعار مكرر. |

### 3.3 الواجهة

`🔙 رجوع` في كل شاشة · `❌ إلغاء` + `/cancel` في كل محادثة · `/start` يخرج من أي محادثة
عالقة · ترقيم `⬅️ 2/5 ➡️` في كل قائمة · كل الأرقام من قاعدة البيانات (لا بيانات تجريبية).

### 3.4 حماية المال والحالة

* تعديل الرصيد يمر حصراً عبر `WalletService.adjust_balance` (خدمة مركزية واحدة).
* الاسترجاع يُنشئ دائماً حركة `refund`؛ لا استرجاع مرتين لنفس الطلب.
* تغيير حالة الطلب يمر عبر آلة الحالات (`core/order_state.py`) حتى في التغيير القسري.
* اعتماد طلب شحن يستخدم `set_status(expected_status=PENDING)` ⇐ الاعتماد المزدوج مستحيل.
* `settings.set` لا تتحقق من نوع القيمة، لذلك يطبّع المعالج القيمة قبل الحفظ
  (`bool → true/false`، `int/money` عبر `normalize_digits`، `json` عبر `json.loads`).

## 5. طريقة التشغيل

```bash
cd smm_bot
python -m venv .venv && source .venv/bin/activate     # ويندوز: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env        # ثم ضع BOT_TOKEN و ENCRYPTION_KEY و SUPER_ADMIN_IDS
python -m scripts.init_db                 # إنشاء القاعدة وتطبيق الترحيلات
python -m scripts.create_admin <telegram_id> --role super_admin
python -m scripts.boot_check              # فحص إقلاع بلا تيليجرام (اختياري ومستحسن)
python -m main                            # تشغيل البوت
```

ثم من داخل تيليجرام: أرسل `/start` ثم اضغط **🛠 لوحة التحكم**، أو أرسل `/admin` مباشرة.

> الزر لا يظهر إلا لمن يملك `admin.access`. إن لم يظهر فتأكد أن حسابك أُنشئ بدور إداري
> عبر `scripts/create_admin.py` (معرّفك يظهر بالأمر `/id`).

## 7. المشاكل والقيود المعروفة

1. **`SettingsService.set` لا تتحقق من نوع القيمة** — الحارس الوحيد اليوم هو
   `_normalize_value` في `handlers/admin/settings.py`. أي مسار كتابة آخر للإعدادات يجب أن
   يطبّع بنفسه. *المقترح للمرحلة 9: نقل التطبيع إلى الخدمة نفسها.*
2. **إنشاء خدمة جديدة غير متاح من اللوحة** — يحتاج اختيار مزود ورقم خدمة عنده، وهذا جزء من
   المرحلة 5. حالياً تُنشأ الخدمات من السكربتات، وكل ما عداها (سعر/إيقاف/أرشفة) من اللوحة.
3. **الإذاعة الجماعية غير موجودة** (المرحلة 8)، ولا **نسخ احتياطي من اللوحة** (المرحلة 10).
4. **لا صفحات للخلف في سجل الأخطاء بعدد كلي** — صفحات الأخطاء تعتمد «الصفحة ممتلئة ⇒ يوجد
   تالٍ» لأن العدّاد الكلي مكلف على جدول ينمو بسرعة.
5. **تحذير `PTBUserWarning: per_message=False`** يظهر عند بناء المحادثات التي تخلط أزراراً
   ورسائل نصية — سلوك متوقَّع في PTB ولا يؤثر على العمل (نفس التحذير موجود منذ المرحلة 3).
6. **ضبط الصلاحيات الفردية (تجاوز لمستخدم بعينه)** يتم اليوم عبر `AuthService` لا من شاشة
   مخصّصة في اللوحة؛ شاشة «إدارة الأدمن والصلاحيات» مجدولة في المرحلة 9.
