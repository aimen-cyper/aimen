**الإصدار:** `0.8.0-phase7` · **الحالة:** مكتملة وجاهزة للمراجعة · **الاختبارات:** 999 ناجحاً / 0 فاشلاً
(193 وحدة + 803 تكامل + 3 دورة كاملة)

## 1. ملخص تنفيذي

كان مسار الشحن يعمل منذ المرحلتين 3 و4: المستخدم يرسل حوالة، والأدمن يعتمد أو يرفض.
لكن فحص الوضع قبل البدء كشف **ثلاث فجوات حقيقية**:

| الفجوة | أثرها العملي قبل المرحلة 7 |
|---|---|
| **طرق الدفع بلا أي واجهة** — دوال `create_method/update_method/set_method_active` موجودة في الخدمة منذ م2 ولا يستدعيها أي معالج | قاعدة بيانات جديدة تبدأ بـ**صفر طرق شحن**، ولا سبيل لإضافة طريقة إلا بـSQL يدوي ⇒ **لا أحد يستطيع شحن رصيده أصلاً** |
| **لا رسوم لكل طريقة** | المحفظة الإلكترونية تقتطع 2.5% فيضطر الأدمن لحساب الفرق ذهنياً وتعديل المبلغ **في كل اعتماد** |
| **قائمة واحدة بلا تصفية ولا بحث** | «حوّلت ولم يصلني الرصيد، رقم العملية كذا» تعني تصفّح الصفحات يدوياً |

المرحلة 7 أغلقت الثلاث:

1. **قسم كامل «🏦 طرق الشحن» داخل اللوحة**: إضافة، تعديل كل حقل، حدود، رسوم، إثبات
   إجباري/اختياري، ترتيب الظهور، تفعيل/إيقاف، وتقرير استخدام.
2. **رسوم لكل طريقة** (نسبة بنقاط الأساس + مبلغ ثابت) تُحسب لحظة الإرسال، **تُخزَّن
   كلقطة داخل الطلب**، ويُضاف الصافي تلقائياً عند الاعتماد — والمستخدم يرى الرقم
   النهائي قبل أن يضغط «تأكيد».
3. **تصفية رباعية + بحث برقم العملية** في شاشة مراجعة الحوالات.

```
/admin → 💰 المدفوعات
   💳 #42 · 200.00 ﷼ · ⏳ قيد المراجعة
      🔢 TRX-99812 · 🕒 2026-10-02 18:40
   [⏳ معلّقة] [✅ معتمدة] [❌ مرفوضة] [📋 الكل]
   [🔎 بحث عن حوالة]  [🏦 طرق الشحن]

/admin → 💰 المدفوعات → 🏦 طرق الشحن → محفظة كريمي
   🧾 الرسوم: 2.5% + 1.00 ﷼   💵 الحدود: الحد الأدنى 10.00 ﷼
   📊 الطلبات: معتمدة 18 · معلّقة 2   💰 أُضيف عبرها: 3,480.00 ﷼
```

**الأرقام:** 4 ملفات جديدة (1,364 سطراً) + 14 ملفاً مُحدَّثاً (و3 ملفات اختبار قائمة) ·
**876 ← 999 حالة اختبار**: 45 اختباراً مكتوباً (11 وحدة + 34 تكامل) و78 حالة أضافها فحص
الأزرار الآلي للوحات الجديدة · 10 معالجات (92 ← 102) و3 محادثات (24 ← 27) و39 زراً
(166 ← 205) · ترحيل `0006` (3 أعمدة + فهرسان + إعدادان).

## 3. ما نُفِّذ فعلياً

### 3.1 إدارة طرق الشحن من اللوحة (الفجوة الأهم)

**الإضافة في 4 خطوات** (الكود الداخلي يُشتق تلقائياً — لا نُجبرك على اختراع معرّف):

```
الاسم  ←  تعليمات التحويل  ←  بيانات الحساب  ←  النوع  ←  مراجعة ← إنشاء
```

**البطاقة بعد الإنشاء** تتيح ضبط كل شيء بزر واحد:

| الزر | ماذا يضبط | التحقق المطبّق |
|---|---|---|
| ✏️ الاسم | الاسم كما يراه المستخدم | 1..64 حرفاً |
| 📋 التعليمات | خطوات التحويل | حتى 600 حرف **مع الحفاظ على الأسطر** |
| 🏧 بيانات الحساب | رقم المحفظة/الحساب | حتى 300 حرف |
| ⬇️/⬆️ الحدود | الحد الأدنى والأقصى | `0` = استخدام الحد العام / إلغاء الحد · ويُرفض أدنى > أقصى |
| ％ / 🧾 الرسوم | نسبة + مبلغ ثابت | النسبة 0..100% · لا قيم سالبة |
| 📎 الإثبات | إجباري أو اختياري | تبديل فوري |
| 🔼/🔽 الترتيب | ترتيب الظهور للمستخدم | تبديل مع الجارة داخل معاملة واحدة |
| ✅/⛔ التفعيل | الظهور للمستخدمين | **لا حذف إطلاقاً** |

قرار مسجَّل: **لا يوجد زر حذف لطريقة الشحن**. الطلبات التاريخية تشير إليها، وحذفها
يكسر سجلاً مالياً — الإيقاف يؤدي الغرض نفسه (تختفي عن المستخدم وتبقى في السجل).

### 3.2 الرسوم: من أين تأتي ولماذا لقطة

```
المستخدم يحوّل 200.00 ﷼ عبر طريقة رسومها 2.5% + 1.00 ﷼
  الرسوم = (200 × 250 + 5000) ÷ 10000  +  1.00  =  6.00 ﷼      ← أعداد صحيحة فقط
  الصافي = 194.00 ﷼   ⇐ يراه المستخدم قبل التأكيد، وهو ما يُضاف عند الاعتماد
```

- **نقاط الأساس (bp)**: 250 = 2.5%. اخترناها لأن النِّسب الكسرية (1.75%) مستحيلة
  بأعداد صحيحة بغير ذلك، و`float` ممنوع في هذا النظام.
- **لقطة على الطلب**: `payments.fee_units` تُكتب لحظة الإرسال. لو رفعت الرسوم غداً،
  الطلب الذي أُرسل اليوم يُعتمد برسوم اليوم — واختبار يحرس هذا حرفياً.
- **الاعتماد يضيف الصافي افتراضياً**، ويبقى زر «✏️ تعديل المبلغ» للحالات الخاصة،
  ويُكتب الفرق في ملاحظة الأدمن وسجل التدقيق.
- **حماية**: مبلغ لا يغطي الرسوم يُرفض عند الإرسال برسالة واضحة، بدل أن يصل الأدمن
  طلبٌ صافيه صفر.
- **شفافية قابلة للتحكم**: إعداد `deposit_fee_visible` (افتراضياً مُفعَّل) يحدد هل
  يرى المستخدم تفصيل الرسوم. إطفاؤه يخفي العرض فقط — **لا يعطّل الخصم**، لأن إخفاء
  خصم حقيقي عن صاحب المال سلوك لا نقبله صامتاً.

### 3.3 مراجعة الحوالات: تصفية وبحث

- **التصفية**: ⏳ معلّقة (الأقدم أولاً — طابور عادل) · ✅ معتمدة · ❌ مرفوضة
  (تشمل الملغى والمنتهي) · 📋 الكل — وكلها الأحدث أولاً.
- **الرجوع يحفظ موضعك**: زر الطلب يحمل التصفية والصفحة، فالعودة من البطاقة تُرجعك
  إلى نفس الصفحة لا إلى البداية.
- **البحث**: برقم العملية (جزئياً أيضاً) أو برقم الطلب، عبر كل الحالات — لأن سؤال
  العميل غالباً عن حوالة رُفضت أو انتهت صلاحيتها.
- **بطاقة الطلب** تفصل الآن: المبلغ المحوَّل · رسوم الطريقة · الصافي للمستخدم.

### 3.4 تقرير طرق الشحن

لكل طريقة: ✅ معتمدة · ⏳ معلّقة · 💰 ما أُضيف فعلاً · 🧾 الرسوم المحصّلة، ثم إجمالي
عام. كل رقم من `SELECT` مباشر على قاعدة البيانات — والطريقة التي لم تُستخدم بعد تظهر
بأصفار صريحة بدل أن تختفي.

### 3.5 لا صمت عند الفراغ

`python -m scripts.boot_check` صار يرفع تحذيراً (ويُحتسب في عدّاد الملاحظات) إن لم
توجد طريقة شحن مفعّلة، وشاشة الأدمن تقول صراحةً «لا يستطيع أي مستخدم شحن رصيده الآن»،
والمستخدم يرى رسالة مفهومة بدل قائمة فارغة.

أهم ما تثبته الاختبارات حرفياً:

- اسمان متطابقان لطريقتين ⇒ **كودان مختلفان** تلقائياً، والجديدة تُضاف آخر القائمة.
- `update_method(code=...)` ⇒ **مرفوض** (الكود معرّف داخلي غير قابل للتعديل).
- نسبة 100.01% ⇒ مرفوضة **قبل** الكتابة، والقيمة القديمة تبقى كما هي.
- حد أدنى 90 مع حد أقصى 50 ⇒ مرفوض برسالة عربية.
- تعليمات «1- حوّل\n2- أرسل» ⇒ تبقى **سطرين** بعد الحفظ.
- 🔼 تبدّل الترتيب فعلياً، وفي قمة القائمة تُرجع `False` بلا تغيير.
- إيقاف طريقة ⇒ تختفي من `active_methods` وتبقى في `all_methods` وطلبها القديم سليم.
- 100 ﷼ عبر طريقة 2.5%+1 ⇒ `fee_units = 3.50` و`net_units = 96.50`.
- رفع الرسوم بعد الإرسال ⇒ **لا يتغير** `fee_units` للطلب القديم.
- الاعتماد الافتراضي يضيف **96.50** لا 100، ورصيد المستخدم يطابقها.
- اعتماد بمبلغ مختلف ⇒ يُنفَّذ وتُسجَّل عبارة «رسوم الطريقة» في ملاحظة الأدمن.
- مبلغ 5 ﷼ مع رسوم ثابتة 20 ﷼ ⇒ **مرفوض عند الإنشاء**.
- التقرير: معتمد 1 · معلّق 1 · المضاف = الصافي · الرسوم = لقطة الطلب.
- شاشة الطرق الفارغة ⇒ نص «لا يستطيع أي مستخدم شحن رصيده» + زر الإضافة.
- دور `support` (يملك `payments.view` بلا `payments.methods`) ⇒ **لا تُرسل له أي شاشة**
  عند محاولة `pm:home`، **ولا يظهر له زر «طرق الشحن»** في قائمة المدفوعات.
- تصفية «معتمدة» لا تعرض المعلّق، و«الكل» تعرض الاثنين.
- البحث برقم العملية يفتح الطلب، والبحث الفاشل يعطي رسالة صريحة.
- محادثة الإضافة الكاملة ⇒ الطريقة تظهر للمستخدمين فوراً.
- `deposit_fee_visible=0` ⇒ يختفي سطر الرسوم من شاشة المستخدم (والخصم باقٍ).
- **الدورة الكاملة**: مستخدم يحوّل 200 ← يرى «سيُضاف لرصيدك 194.00» ← أدمن يعتمد ←
  رصيده **194.00 بالضبط**.

## 9. متطلب أعرضه عليك قبل تنفيذه (لم يُنفَّذ)

**عملة مستقلة لكل طريقة شحن + سعر صرف.**

- **لماذا قد تحتاجه:** إن أضفت USDT أو حوالة بالدولار، المستخدم يحوّل 10 USDT بينما
  رصيد النظام بالريال. اليوم يجب أن يُدخل المبلغ بعملة النظام ويحسب هو سعر الصرف.
- **أين يؤثر:** عمودان في `payment_methods` (`currency`, `rate_to_base_units`) + عمودان
  لقطة في `payments` + شاشة تعديل السعر + تحويل عند العرض والاعتماد + تقرير مزدوج العملة.
- **هل يحتاج تعديل DB/تدفقات؟** نعم: ترحيل جديد + تعديل شاشتي الشحن والاعتماد.
- **رأيي:** لا تبدأه إلا إن كنت ستستقبل فعلاً عملة غير عملة النظام؛ وإلا فهو تعقيد بلا
  مقابل. **بانتظار قرارك — لن أنفّذه بلا موافقة صريحة.**

## 10. الالتزام بالقواعد الملزِمة

| القاعدة | التطبيق في هذه المرحلة |
|---|---|
| تغيير الرصيد من خدمة مركزية واحدة | الإضافة كلها عبر `WalletService.credit_from_payment` داخل معاملة الاعتماد — لم يُضف أي مسار جديد |
| لا عملية مالية بلا Transaction ومرجع فريد | بلا تغيير: الاعتماد ينشئ حركة بمرجع `payment:<id>` |
| لا تغيير حالة بلا تحقق من السابقة | `set_status(expected_status='pending')` كما هي + آلة الحالات |
| لا حذف بيانات تاريخية | لا زر حذف لطريقة الشحن؛ الإيقاف فقط، واختبار يثبت بقاء الطلب القديم |
| فحص الصلاحية على الـcallback | `payments.methods` لكل إجراء إداري، و`payments.view` للقراءة — ومُختبران بدور `support` |
| لا زر بلا وظيفة | 205 أزرار مفحوصة آلياً، صفر زر يتيم |
| لا أرقام ثابتة ولا بيانات وهمية | لا طريقة شحن مزروعة؛ الأدمن يُنشئ طرقه الحقيقية، والنظام ينبّه ما دامت فارغة |
| أعداد صحيحة للمال | الرسوم بنقاط الأساس وحساب صحيح 100%، واختبار يمنع تسرّب `float` |
| تعليق عربي بجانب كل دالة | كل دالة جديدة لها docstring تشرح عملها وسبب قرارها |
