## 2) ما نُفِّذ فعلياً

### 2.1 المخطط: 28 جدولاً (27 + جدول تتبع الترحيلات)

### 2.2 الضمانات المالية (نُفِّذت على مستوى قاعدة البيانات لا الكود فقط)

| الخطر | الحماية المنفَّذة |
|---|---|
| رصيد سالب | `CHECK (balance_units >= 0)` + `UPDATE … WHERE balance_units >= ?` + فحص `rowcount` + تسلسل الكتابة بقفل واحد |
| خصم مزدوج عند الضغط المتكرر | `orders.client_request_id` فريد + جدول `idempotency_keys` |
| استرجاع مزدوج | `transactions.reference` فريد + `CHECK (refund_amount_units <= cost_units)` |
| إشعار مكرر | `notifications.dedupe_key` فريد `NOT NULL` |
| طلب مزدوج عند المزود | فهرس فريد جزئي على `(provider_id, provider_order_id)` |
| تغيير حالة عشوائي | كل تحديث حالة مشروط بالحالة السابقة ويُرجع `False` بدل الكتابة فوق عمل غيره |
| ضياع الدقة | لا عمود `REAL` في المخطط إطلاقاً — المال `INTEGER` بمقياس 1/10,000 |
| فقدان التاريخ | `transactions` للإضافة فقط، والخدمات تُؤرشف ولا تُحذف، ولا `CASCADE` على أي جدول مالي |

### 2.3 الأمان

- مفاتيح المزودين تُخزَّن **مشفَّرة** (Fernet)، ويُحفظ بجانبها تلميح بآخر 4 محارف للعرض فقط.
- `SecretRedactionFilter` على كل اللوقات + `sanitize()` قبل تخزين أي استجابة مزود أو رسالة خطأ.
- الصلاحيات كلها في قاعدة البيانات (43 صلاحية)، و`SUPER_ADMIN_IDS` للزرع الأولي والطوارئ فقط.
- لا أسرار في الكود؛ كل شيء من `.env`، و`safe_summary()` تطبع «✓ موجود» بدل القيمة.

### 2.4 الجاهزية للمراحل القادمة

- `notifications` (Outbox) جاهز لإرسال الإشعارات في نفس معاملة تغيير الحالة → لا إشعار بلا حدث ولا حدث بلا إشعار.
- `orders` فيها أعمدة الحجز (`locked_by` / `locked_until` / `next_check_at`) لعمّال المرحلة 6.
- `user_states` تحفظ حالة المحادثة في القاعدة → المستخدم لا يفقد مكانه عند إعادة تشغيل البوت.
- `idempotency_keys` جاهز لحماية أزرار الأدمن الحساسة.

## 6) المشاكل التي ظهرت والقيود المعروفة

### 6.1 مشاكل اكتُشفت وأُصلحت أثناء التنفيذ

| المشكلة | الخطر | الإصلاح |
|---|---|---|
| `executescript` في بايثون **يُثبِّت أي معاملة مفتوحة قبل التنفيذ** — كشفه اختبار التراجع: جدول من ترحيل فاشل بقي موجوداً | ترحيل يفشل في منتصفه يترك المخطط **نصف مطبَّق** | أُعيدت كتابة `_apply_one`: تقسيم الملف بـ `sqlite3.complete_statement` وتنفيذ العبارات واحدة واحدة داخل معاملة واحدة، مع رفض `BEGIN/COMMIT/PRAGMA` داخل ملفات الترحيل |
| `sanitize()` لم تكن تحذف الأسرار المكتوبة بصيغة JSON مثل `"api_key": "abc"` | تسرّب مفتاح في سجل استجابات المزود | وُسِّعت الأنماط لتشمل القيم بين علامتي اقتباس وأسماء إضافية (`access_token`, `auth_token`, `passwd` …) |
| اختلاف حرف واحد بين اسم صلاحية في الكود وفي ملف الزرع | تباعد صامت بين الكود وقاعدة البيانات | وُحِّد الاسم، ويحرس ذلك الآن اختبار يقارن **الاسم والمجموعة ودرجة الخطورة** لكل صلاحية |

### 6.2 قيود معروفة (مقصودة ومُوثَّقة)

1. **الإشعارات `at-least-once`** — إن انقطع البوت بين الإرسال الفعلي وتعليم الإشعار كمُرسل، قد يصل الإشعار مرتين. مقبول لأنه إشعار نصي لا عملية مالية.
2. **كاتب واحد** — SQLite تسمح بكاتب واحد في اللحظة؛ الكتابة متسلسلة بقفل. كافٍ تماماً لآلاف المستخدمين، وعند الحاجة للتوسّع يُنتقل إلى PostgreSQL (الاستعلامات مكتوبة بـ SQL قياسي لتسهيل ذلك).
3. **`submit_uncertain` تحتاج تدخلاً بشرياً** — عند انقطاع الاتصال أثناء الإرسال لا يُعاد الإرسال آلياً (منعاً للطلب المزدوج)؛ تُعرض للأدمن في المرحلة 6 مع زر ربط يدوي.
4. **لا واجهة بعد** — هذه المرحلة طبقة بيانات فقط؛ لا يوجد `main.py` ولا معالجات تيليجرام (المرحلتان 2 و3).
5. **`payment_methods` فارغ عمداً** — لا بيانات وهمية؛ تُضاف طرق الدفع الحقيقية من لوحة الأدمن في المرحلة 5.
6. **إعادة تعيين مفتاح التشفير** غير مدعومة آلياً بعد؛ تغييره يتطلب إعادة إدخال مفاتيح المزودين (أداة إعادة التشفير مؤجلة للمرحلة 11).

المرحلة 2 المقترحة = **طبقة الخدمات (Services Layer)**: `WalletService` (الجهة الوحيدة التي تلمس الرصيد)، `OrderService`، `PaymentService`، `NotificationService`، `AuthService`، `SettingsService` — أي منطق الأعمال فوق المستودعات، مع اختبار الدورة المالية الكاملة (خصم → استرجاع → دفتر متوازن).

⏸️ **لن أبدأ المرحلة 2 إلا بعد موافقتك الصريحة.**
