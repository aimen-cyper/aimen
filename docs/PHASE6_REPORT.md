# تقرير المرحلة 6 — المهام الدورية والمتابعة الآلية المتقدمة

**الإصدار:** `0.7.0-phase6` · **الحالة:** مكتملة وجاهزة للمراجعة · **الاختبارات:** 876 ناجحاً / 0 فاشلاً
(182 وحدة + 691 تكامل + 3 دورة كاملة)

---

## 1. ملخص تنفيذي

بعد المرحلة 5 صار البوت يتكلم مع مزوّد حقيقي، لكن «التشغيل الذاتي» كان ما يزال هشاً في
ثلاث نقاط: المهام الدورية بلا إشراف (استثناء واحد يوقف مهمة بصمت إلى الأبد)، وفحص حالات
الطلبات يستهلك استدعاء HTTP لكل طلب، ولا أحد يراقب المزوّد إلا عند حدوث الطلب.

المرحلة 6 عالجت الثلاثة:

1. **طبقة إشراف على كل مهمة** (`jobs/runner.py`): منع التداخل، مهلة قصوى لكل جولة، التقاط
   كل استثناء إلى `error_logs`، تنبيه الأدمن عند تكرار الفشل، وسجل حالة حيّ.
2. **الفحص الجماعي للطلبات**: الطلبات تُجمَّع حسب المزود ويُستعلَم عنها بطلب HTTP واحد
   (`multi-status`) — دفعة من 20 طلباً صارت استدعاءً واحداً بدل عشرين.
3. **مراقبة استباقية ورؤية**: مهام جديدة لأرصدة المزودين وصحتهم وملخص يومي وصيانة
   قاعدة البيانات، وشاشة **«⏱ المهام الدورية»** داخل اللوحة تُظهر نبض النظام وتسمح
   بتشغيل أي مهمة فوراً.

```
/admin → 🩺 صحة النظام → ⏱ المهام الدورية
   🟢 🔄 متابعة حالة الطلبات   ⏲ كل 2 دقيقة · آخر تشغيل: 20:41
      🔁 جولات: 48 · ⚠️ إخفاقات: 0 · ⏭ تخطٍّ: 0 · ⌛️ 0.3 ثانية
   🔴 💵 فحص أرصدة المزودين    🐞 آخر خطأ: انقطاع الاتصال بالمزود
      ▶️ تشغيل الآن · أرصدة المزودين
```

**الأرقام:** 4 ملفات إنتاجية جديدة (612 سطراً) + 11 ملفاً مُحدَّثاً · ملفا اختبار جديدان
(657 سطراً) · 32 اختباراً جديداً (844 ← 876) · مهمتان دوريتان ومهمتان يوميتان جديدتان
(6 ← 10) · شاشتان جديدتان في اللوحة (92 معالجاً، 166 زراً) · 8 إعدادات جديدة · ترحيل
`0005` **بلا أي تغيير في المخطط**.

> **قرارك المسجَّل في هذه المرحلة:** إبقاء `priority` (أولوية المزود) وربط الخدمة بأكثر من
> مزوّد **كما هو — موجود وغير مستعمل**، تستخدمه لاحقاً عند الحاجة. لذلك لم يُنفَّذ أي
> تحويل تلقائي لمزود بديل، وبقي سلوك الفشل كما اعتمدته: تنبيه + استرجاع آمن.

آلاف عمليات كتابة يومياً بلا قيمة تاريخية؛ أما ما يستحق البقاء — الأخطاء — فيُكتب في
`error_logs` فعلاً. الشاشة تقول ذلك صراحةً للمستخدم.

### 3.2 الفحص الجماعي: نفس المنطق، عُشر الاستدعاءات

```
قبل:  20 طلباً مستحقاً  ⇒ 20 طلب HTTP  (status لكل طلب)
بعد:  20 طلباً لمزودين اثنين ⇒ 2 طلب HTTP (multi-status لكل مزود)
```

- التجميع حسب `provider_id`، ثم `fetch_multi_status` لكل مجموعة.
- **المسار الاحتياطي الفردي** لكل طلب لم يُجب عنه المزود في الدفعة (بعض اللوحات تُسقط
  الطلبات القديمة من الرد الجماعي) — فلا طلب «يضيع» بصمت.
- فشل الاستعلام الجماعي (انقطاع/مهلة) ⇒ تُفك أقفال كل طلبات المجموعة ويُؤجَّل فحصها
  بالتدرج التصاعدي المعتاد، **بلا تغيير حالة وبلا استرجاع** — لأن تعذّر القراءة ليس فشلاً
  للطلب.
- قابل للإطفاء من اللوحة: إعداد `order_multi_status_enabled` لمزوّد لا يدعم الاستعلام
  الجماعي (حينها يعود الفحص فردياً تلقائياً).
- كل استدعاء جماعي يُسجَّل في `provider_requests` بالصيغة `multi-status count=N` فيبقى
  أثره قابلاً للتدقيق.

### 3.4 حدود صيانة قاعدة البيانات (التزاماً بقاعدة «لا حذف للبيانات التاريخية»)

| تفعل | لا تفعل |
|---|---|

| `PRAGMA wal_checkpoint(TRUNCATE)` لتقليص ملف الـWAL | `VACUUM` التلقائي (يقفل القاعدة طويلاً — يبقى قراراً يدوياً) |
| `PRAGMA optimize` لتحديث إحصاءات المخطط | أي تعديل على بنية الجداول |

### 3.5 شاشة «⏱ المهام الدورية»

- **العرض** بصلاحية `stats.view`: لكل مهمة أيقونة حالة (🟢 سليمة · 🔴 متعثرة · 🏃 تعمل الآن
  · ⚪️ لم تعمل بعد)، جدولتها، آخر تشغيل، عدد الجولات والإخفاقات والتخطّيات، زمن آخر جولة
  ومتوسطه، وآخر خطأ إن وُجد.
- **«تشغيل الآن»** بصلاحية `settings.maintenance` فقط — لأنه تدخل تشغيلي حقيقي (قد يستدعي
  المزود أو يرسل إشعارات) لا مجرد قراءة. ويمر على **نفس الغلاف المُشرِف**، فلو كانت المهمة
  تعمل فعلاً رُفض التشغيل، ولو فشلت ظهر خطؤها في رسالة النتيجة وسُجّل في `error_logs`.

أهم ما تثبته الاختبارات حرفياً:

- مهمة ترمي استثناءً ⇒ **لا يُرفع الاستثناء** خارج الغلاف، ويُكتب سطر في `error_logs`
  مصدره `job:<name>`، والعدّادات تتحدّث.
- بعد بلوغ حد الإخفاقات (2 في الاختبار) ⇒ إشعار «مهمة دورية متعثرة» في طابور الأدمن.
- جولة بطيئة ما زالت تعمل + جولة جديدة ⇒ `skipped == 1` و`runs == 0` (لا تداخل ولا فشل).
- مهمة لا تنتهي + مهلة 50ms ⇒ تُحتسب فشلاً ولا تُعلَّق.
- 3 طلبات لمزود واحد ⇒ **صف واحد** في `provider_requests` بـ`multi-status count=3`.
- ردّ جماعي ناقص ⇒ الطلب غير المُجاب عنه يُفحص فردياً (ظهور استدعاء `status`).
- فشل الاستعلام الجماعي ⇒ الطلبان يبقيان بحالتهما، `locked_by is None`، و`unchanged == 2`.
- مهمة الأرصدة ⇒ `balance_units` محدَّث + لقطة واحدة في `provider_balance_snapshots`؛
  وتنبيه الانخفاض يصل مرة واحدة لا في كل جولة.
- مزود عليه 3 إخفاقات وانتهت مدة إيقافه ⇒ `consecutive_failures = 0`, `disabled_until = NULL`,
  وإشعار «تعافى مزود»؛ ومزود ما زال في مدة الإيقاف **لا يُختبر**.
- الملخص اليومي يُدرج مرة واحدة لليوم (الاستدعاء الثاني يُرجع `False`).
- الصيانة تحذف المفتاح المنتهي فقط، ويبقى المفتاح الصالح وعدد المستخدمين كما هو.
- شاشة المهام تعرض الحالتين 🟢/🔴 وآخر خطأ؛ ومن يملك `stats.view` بلا `settings.maintenance`
  **لا يرى أي زر تشغيل**؛ وتشغيل مهمة غير مجدولة يُرفض برسالة واضحة.

## 10. الالتزام بالقواعد الملزِمة

| القاعدة | التطبيق في هذه المرحلة |
|---|---|
| لا حذف للبيانات التاريخية | الصيانة تحذف مفاتيح منع التكرار المنتهية فقط — واختبار يتأكد أن بقية البيانات سليمة |
| لا تغيير حالة طلب بلا تحقق | الفحص الجماعي يمر على نفس `_apply_status` وجدول الانتقالات؛ فشل القراءة لا يغيّر حالة |
| لا تكرار طلب | التجميع لا يمسّ مسار الإرسال؛ الحجز (lease) كما هو، والتداخل ممنوع بقفل |
| لا إخفاء أخطاء | كل استثناء مهمة يُسجَّل في `error_logs` + تنبيه عند التكرار؛ لا `except: pass` |
| فحص الصلاحية على الـcallback | `stats.view` للعرض و`settings.maintenance` للتشغيل اليدوي، ومُختبران |
| لا زر بلا وظيفة | 166 زراً مفحوصاً آلياً، صفر زر يتيم |
| لا أرقام ثابتة في الكود | 8 إعدادات جديدة تضبط كل إيقاع المهام وأحجام الدفعات |
| تعليق عربي بجانب كل دالة | كل دالة جديدة لها docstring تشرح وظيفتها وسبب قرارها |

## 11. الوضع مقابل خطة المراحل

| المرحلة | الحالة |
|---|---|
| 0–5 | ✅ مكتملة |
| **6 — المهام الدورية والمتابعة الآلية** | ✅ **مكتملة (هذا التقرير)** |
| 7 — نظام الدفع والشحن المتقدم | ⏳ التالية (بانتظار موافقتك) |
| 8–12 | ⏳ حسب الخطة |

**ما تتوقعه المرحلة 7 (للاطلاع فقط، لن أبدأها إلا بموافقتك):** طرق دفع متعددة قابلة
للإدارة من اللوحة (إضافة/تعديل/ترتيب/تفعيل)، رسوم وحدود لكل طريقة، إثبات إجباري أو
اختياري حسب الطريقة، وشحن يدوي بمرجع عملية — مع إبقاء كل تغيير للرصيد في `WalletService`
وحده كما هو الآن.
